This post will run through the labs on web sec academy by Portswigger related to JWT attacks.

JWT stands for json web token and is made up of three parts: header, payload and signature.

### <u>Lab: JWT authentication bypass via unverified signature
Sometimes developers use decode() instead of verify() when checking JWTs so by putting any signature we can bypass authentication. In this lab when we try access /admin we are told "Admin interface only available if logged in as an administrator". We also see in our GET request to /admin we include a session cookie which is a JWT which when decoded shows:  
HEADER
```
{
  "kid": "17db250c-22cc-404a-a400-a9b1aa40bd7f",
  "alg": "RS256"
}
```
PAYLOAD
```
{
  "iss": "portswigger",
  "exp": 1751985136,
  "sub": "wiener"
}
```
Now all we have to do is create our own JWT with the "sub" field changed to adminstrator and then send the request using that token.

### <u>Lab: JWT authentication bypass via flawed signature verification
As you saw in the last lab te header includes the hashing algorithm being used however it can also be set to none so it would have no signature. These tokens are usually rejected through filtering however if the filtering is bypassed you can get them accepted. In this lab it isn't filtered so we can just set the token to have the header:
```
{
  "kid": "42b647a6-0275-42c1-8fe6-6609c474dc78",
  "alg": "none"
}
```
And then our payload:
{
  "iss": "portswigger",
  "exp": 1751987188,
  "sub": "administrator"
}

### <u>Lab: JWT authentication bypass via weak signing key
Secret keys in jwt tokens can also be brute forced with hashcat using a wordlist of secrets that get used alot. This can be done using the command:
```
hashcat -a 0 -m 16500 <jwt> <wordlist>
```
After running my command with the wordlist from https://github.com/wallarm/jwt-secrets/blob/master/jwt.secrets.list , i got my secret to be secret1. Then using the site https://10015.io/tools/jwt-encoder-decoder , i was able to encode a JWT with the secret and having my user changed to administrator.

### <u>Lab: JWT authentication bypass via jwk header injections
While only the alg parameter is required for header there some other parameters interesting for attacking:
- jwk - Embedded json representing the key
- jku - URL which servers can fetch keys containing the correct key
- kid - ID that servers can use to identify the correct key

Sometimes servers might be misconfigured so they use the key inside the jwk parameter. This would allow us to create our own key and sign a custom JWT which is what we do in this lab. To do this we will use a burp extension called JWT editor which makes the process easier. First we will go to the JWT editor tab and create a RSA key, then we will try access /admin and send that request to burp repeater. In burp repeater there is a tab for JWT where we can press attack and select "Embedded JWK" which automatically sets up the header and payload for us. It should look like this:
