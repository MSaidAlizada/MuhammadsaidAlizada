This post will run through the labs on web sec academy by Portswigger related to SSRF. 

Server-side request forgery is a web security vulnerability that allows an attacker to cause the server-side application to make requests to an unintended location.

### <u>Lab: Basic SSRF against the local server
In an SSRF attack against the server, the attacker causes the application to make an HTTP request back to the server that is hosting the application, via its loopback network interface. By having the local machine send the request we can bypass access controls since the local machine is usually trusted.  

For example in this lab there is a stock check feature where it makes an API call which is sent in the HTTP request. We can modify where it makes the API call to "http://localhost/admin" which gives us access to the admin panel where we see we can delete the user carlos through this call "/admin/delete?username=carlos". Now by changing the API call to that we can delete carlos.

### <u>Lab: Basic SSRF against another back-end system
This lab is similar to the last but this time we are told the admin panel can be searched for in the range 192.168.0.X in the port 8080. So we can use burp intruder to go through all X from 1 to 255 to see which gives us a status code of 200.
```
stockApi=http://192.168.0.~:8080/admin
```
I found it to be at 39 and so by sending the request with this API url we can delete carlos: http://192.168.0.39:8080/admin/delete?username=carlos

### <u>Lab: SSRF with blacklist-based input filter
In this lab there is a filter on the url we send for example it catches if we use localhost or admin within the url. To bypass this we can first use 127.1 instead of 127.0.0.1 and localhost and then we can also obfuscate the word admin through url encoding. However one url encoding is not enough to bypass the filter so we will double encode admin and then we have bypassed the filter.
```
http://127.1/<@urlencode_all><@urlencode_all>admin</@urlencode_all></@urlencode_all>/delete?username=carlos
```

### <u>Lab: SSRF with filter bypass via open redirection vulnerability
Other applications only allows urls which match whitelisted values which can be bypassed through inconsistent url parsing. If the API used to make the back-end HTTP request supports redirections, you can construct a URL that satisfies the filter and results in a redirected request to the desired back-end target. For example:
```
POST /product/stock HTTP/1.0
Content-Type: application/x-www-form-urlencoded
Content-Length: 118

stockApi=http://weliketoshop.net/product/nextProduct?currentProductId=6&path=http://192.168.0.68/admin
```
In this lab since the stock check feature takes a path we can give it our own url since it would just append it to the already existing url. Instead we have to find an open redirect which we find in the next product feature since it takes path as parameter. By giving the url to the next product feature with the redirect set to the admin panel, to stock check we can get access to the admin panel and delete the user carlos.
```
stockApi=/product/nextProduct%3fcurrentProductId%3d2%26path%3dhttp%3a//192.168.0.12%3a8080/admin/delete?username=carlos
```
